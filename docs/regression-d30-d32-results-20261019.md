## D-32：导入延迟、丢批次与重复导入

代码中确认存在两个能导致报告所述现象的机制：原 `saveDb()` 发起云端写入后不等待结果，接口随即返回成功；不同服务实例持有独立旧数据库，并各自无条件上传整份快照，后完成的旧快照可以覆盖较新的任务数据。原前端在收到成功响应后关闭弹窗、整页刷新，掩盖了尚未确认落库的状态。

修复如下：

- 云端请求从最新快照创建独立的数据库上下文，提交时检查快照修订号。发现并发修改则返回 409，拒绝旧快照覆盖；云端读取或保存失败返回错误，不降级为种子数据库覆盖云端。
- 统一 API 请求的保存边界，等待远端提交完成后才把成功响应交给用户。其他接口也纳入同一边界，避免它们继续用旧快照覆盖计划书导入结果。
- 任务、子任务、里程碑和导入回执在同一事务中生成。任何步骤失败整批回滚。
- 导入使用批次编号和持久化回执。重复提交返回已有结果，不重复创建任务、子任务或里程碑；网络中断后的重试可以复用同一批次。
- 前端按计划书内容生成批次编号；重新选择已保存的同一份文件时读取回执并提示已导入。保存期间持续显示状态，禁用重复提交及关闭，不再整页跳转；确认保存后刷新看板并显示任务数量。并发冲突可安全重试。

验证证据：

1. 控制远端提交暂停，确认接口尚未返回成功；放行提交后新请求能读到数据。
2. 两个独立请求先后读取相同旧版本，让后一个先提交。前一个迟到提交被拒绝；重试后两批数据都存在。
3. 模拟远端写失败，返回 503，远端数据未被内存中的未提交修改污染；模拟读取失败，没有上传种子库。
4. 并发重复导入同一批次，仅一组任务和里程碑生成；导入第二批后第一批仍保留。批次后段故意失败时，前段任务及回执均回滚。
5. 实际 Chrome 中暂停导入请求，弹窗显示保存状态；重复触发按钮未产生多次提交。模拟服务端已写入但响应丢失，前端显示重试提示，重试后两批共四个标记任务各保留一份。刷新后仍在；再次选择同一文件提示已经保存。

## D-31：按账号保存日志与撤销/重做历史

新增账号操作记录接口与存储，分别保存日志、历史快照和各文档的撤销位置。登录时从服务端加载并合并该账号的本地旧记录，后台同步后续操作；退出登录前等待记录保存。仍保留账号隔离的本地缓存，界面显示同步状态，失败可以重试。

日志按 ID 去重，历史按快照 ID 去重。只接收当前账号拥有的文档快照，读取同样按账号过滤。明确清空日志会保留历史，并记录已清空的日志 ID，防止另一设备的旧缓存把日志重新上传回来。

实际 Chrome 验证：编辑产生明确内容差异后，执行真实退出登录，清空 localStorage，再重新登录；日志和历史从服务端恢复。实际点击撤销后 API 内容改变，点击重做后内容还原。另开无缓存的新浏览器会话登录，也能读取同一账号日志和快照。专项接口测试覆盖账号隔离、重复上传、快照位置及清空后的旧缓存重放。

保留范围为最近 100 条日志、50 条历史快照。这是账号操作记录同步，不是不可删除、永久保存的合规审计系统。升级前已经彻底删除且没有其他备份的本地记录，无法凭此改动追溯重建。

## D-30：历史恢复的键盘操作

原实现中整行快照是按钮，但“恢复此版本”字样是行内 div，操作目标不够明确。现改为可见、独立的原生 button，提供包含时间和卡片数的可访问名称以及键盘焦点样式，保留二次确认和恢复前备份。

真实 Chrome 验证：从面板关闭按钮按 Tab 到恢复按钮，检查实际焦点，再按 Enter 打开恢复确认，Esc 取消。恢复及撤销的既有回归也通过。
